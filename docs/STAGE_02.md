# Этап 02. Модель памяти и правила доступа

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 01](STAGE_01.md)

## Что меняется после первого этапа

Этап 01 научил приложение запускаться и отвечать на `GET /health`.
Теперь добавляем предметную часть: какие объекты участвуют в доступе к памяти,
как связаны сотрудник и агент, какие права нужны для конкретного действия,
почему запрос разрешён или отклонён.

Работаем на чистом Python и вымышленных данных. Функция получает объекты,
проверяет их и возвращает решение. Она не читает документ для клиента,
не изменяет его и не обращается к базе. Это позволяет разобрать правила
отдельно от сети, хранения и вызова модели.

Например, в компании Alpha есть финансовый и инженерный проекты.
У финансового сотрудника есть право чтения финансового документа. Его агенту
делегировано чтение в финансовом проекте. Оба условия соблюдены — проверка
разрешает запрос. Если право сотрудника отозвано, широкое делегирование
агента не должно сохранить доступ. Если у сотрудника есть право, но агенту
не делегировано это действие, результат также должен быть отказом.

## Граница этапа

Реализованы неизменяемые модели, проверка входных значений, детерминированная
политика доступа, модель события попытки проверки и офлайн-демонстрация.
Текущие результаты тестов и публикации записаны в [отчёте](VERIFICATION.md).

Пока нет постоянного хранилища документов, истории версий в БД, аутентификации,
HTTP-маршрутов памяти, поиска, агента с моделью и корпоративного коннектора.
Создание Python-объекта документа не означает загрузку в сервис.
Переданный `employee_id` — входные данные, а не доказательство личности.
Событие аудита существует только в памяти процесса и не становится журналом
действий автоматически.

## 1. Запустить демонстрацию

Из корня репозитория:

```bash
uv sync --locked
uv run --locked python -m app.demo
```

Вторая команда выполняет модуль `app/demo.py`. Сервер Uvicorn для неё
не нужен. Демонстрация создаёт вымышленные объекты, проверяет несколько
запросов и показывает исходы с кодами причин. Данные и время заданы явно,
поэтому одинаковый запуск даёт одинаковый результат.

Вывод — JSON-массив со следующими сценариями:

| `case` | `allowed` | `reason` |
| --- | --- | --- |
| `finance_read` | `true` | `allowed` |
| `engineering_finance_denied` | `false` | `project_mismatch` |
| `foreign_company_denied` | `false` | `company_mismatch` |
| `missing_grant_denied` | `false` | `employee_permission_missing` |
| `revoked_delegation_denied` | `false` | `delegation_unavailable` |
| `write_denied` | `false` | `employee_permission_missing` |
| `version_mismatch_denied` | `false` | `version_mismatch` |
| `action_not_delegated` | `false` | `action_not_delegated` |

У каждой строки также есть `request_id`, действие `action` и время
`occurred_at`. Демонстрация использует фиксированное время
`2026-10-24T00:00:00+00:00`; это данные сценария, а не время вашего запуска.
Текст документов не печатается, события не сохраняются. Функция
`demo_results()` создаёт объекты и возвращает пары имени случая и решения.
`main()` создаёт события с заданным временем и печатает только метаданные JSON.

Модуль не импортирует `app.main` и не загружает настройки `APP_*`.
Для него не нужны `.env`, ключ модели или корпоративные учётные данные.

## 3. Разобраться с объектами

| Модель | Что означает |
| --- | --- |
| `Company` | Компания — внешняя граница данных |
| `Project` | Проект внутри одной компании |
| `Employee` | Сотрудник с принадлежностью к компании |
| `Agent` | Зарегистрированный агент, связанный с компанией и сотрудником |
| `Delegation` | Что этот сотрудник делегировал этому агенту в одном проекте |
| `Document` | Идентификатор документа, его компания, проект и заголовок |
| `DocumentVersion` | Идентификатор версии, номер, источник и ограниченный текст |
| `Grant` | Разрешённые действия сотрудника над конкретным документом |
| `AccessRequest` | Кто, каким агентом, над какой версией и какое действие запрашивает |
| `AccessDecision` | Точный запрос, разрешение или отказ и код причины |
| `AuditEvent` | Метаданные попытки проверки и явно переданное время |

`Document` и `DocumentVersion` разделены: документ может иметь несколько
редакций, а запрос должен указывать конкретную. На этом этапе связь проверяется
по идентификаторам, а неизменяемый объект хранится только в памяти. Уникальность
номеров, постоянная история и конкурентное изменение появятся с хранилищем.

`Grant` и `Delegation` тоже решают разные задачи. `Grant` отвечает, что разрешено
сотруднику над документом. `Delegation` ограничивает действия агента в проекте.
Одно не заменяет другое. Разрешение для другого сотрудника, документа или
проекта не подходит текущему запросу.

## 4. Почему используются dataclass, frozen и frozenset

`dataclass` описывает объект через поля и создаёт обычные методы сравнения
и инициализации. `frozen=True` запрещает обычное присваивание нового значения
полю после создания. `slots=True` ограничивает набор атрибутов объекта.

Например, статус отозванного разрешения задаётся новым объектом:

```python
from dataclasses import replace

revoked_grant = replace(grant, active=False)
```

`grant` остаётся прежним снимком, а `revoked_grant` представляет новые данные.
После изменения нужно снова вызвать политику. Старое положительное решение
не превращается в постоянный пропуск к данным.

Набор действий задаётся через `frozenset`: это множество, которое нельзя
обычным методом дополнить или очистить после создания.

```python
from app.domain.models import Action

read_only = frozenset({Action.READ})
read_and_write = frozenset({Action.READ, Action.WRITE})
```

`Action` — `StrEnum`, перечисление допустимых строковых значений. В модели
разрешены именно `Action.READ` и `Action.WRITE`, а не произвольные строки.
Передать обычный список или `set` вместо `frozenset` нельзя. Пустое множество
допускается, но не разрешает ни одного действия. Право `write` не даёт `read`
автоматически; для двух действий нужны два явных значения.

Неизменяемость помогает рассуждать о функции, но не устанавливает доверие.
Другой Python-код всё равно способен создать новый объект с вымышленными
идентификаторами. Проверять происхождение этих объектов будет будущий
прикладной слой с аутентификацией и хранилищем.

## 5. Что проверяется при создании модели

Метод `__post_init__()` выполняется после заполнения полей `dataclass`.
Он вызывает небольшие функции проверки значений:

- `_validate_id()` принимает от 1 до 128 ASCII-символов: сначала буква или
  цифра, далее также допустимы `_`, `.`, `:` и `-`.
- `_validate_label()` проверяет однострочные имя, заголовок и обозначение
  источника: от 1 до 256 печатных символов без пробелов по краям.
- `_validate_active()` принимает настоящий `bool`, без преобразования `1`
  или строки `"true"`.
- `_validate_actions()` принимает неизменяемое множество значений `Action`.

`DocumentVersion.number` — целое число от 1 до 1 000 000; `True` не подходит,
хотя Python считает `bool` разновидностью `int`. Текст версии должен содержать
от 1 до 20 000 символов. Переносы строк в тексте допустимы. Обозначение `source`
пока является метаданными, его существование в корпоративном сервисе не
проверяется.

Содержимое версии исключено из автоматического `repr()`, поэтому случайный
вывод объекта не печатает весь документ. Это не механизм защиты: поле `content`
остаётся доступным обычному Python-коду. Не помещайте сюда реальные
корпоративные данные на этом этапе.

`AccessDecision` проверяет согласованность: `allowed=True` допустимо только
с `ReasonCode.ALLOWED`. У отказа должна быть другая причина. Несогласованный
результат нельзя незаметно передать дальше как корректную модель.

## 6. Проследить проверку доступа

Сигнатура принимает запрос и один явно переданный снимок объектов:

```python
decision = evaluate_access(
    request,
    company=company,
    project=project,
    employee=employee,
    agent=agent,
    delegation=delegation,
    document=document,
    version=version,
    grants=(grant,),
)
```

Запись `(grant,)` — кортеж с одним элементом. Кортеж сохраняет набор
предоставленных разрешений неизменяемым на время этой проверки. Если прав нет,
можно передать пустой кортеж; стандартное значение `grants` также пустое.

Порядок проверки фиксирован:

1. Компания существует, активна и соответствует запросу.
2. Проект активен, соответствует запросу и принадлежит этой компании.
3. Сотрудник активен, выбран верно и принадлежит этой компании.
4. Агент активен, выбран верно и связан с этим сотрудником и компанией.
5. Делегирование активно, совпадает по сотруднику, агенту, компании и проекту;
   запрошенное действие входит в него.
6. Документ активен и соответствует запрошенным идентификатору и области.
7. Версия активна, выбрана верно и принадлежит этому документу и компании.
8. Есть активный `Grant` для этого сотрудника, документа, компании, проекта
   и запрошенного действия.

Первая нарушенная предпосылка определяет код отказа. Поэтому при нескольких
ошибках функция возвращает один предсказуемый результат. Порядок не является
списком всех проблем входа и не заменяет будущую политику HTTP-ошибок.

Например, у финансового сотрудника есть `Grant` только на чтение.
Его агенту делегированы чтение и запись. Для `READ` обе стороны разрешают
действие, результат — `allowed`. Для `WRITE` делегирование подходит, но
права сотрудника нет: `employee_permission_missing`.

Функция возвращает только `AccessDecision`. Она не вызывает метод чтения
и не возвращает поле `content`. Даже положительный результат означает только
«этот предоставленный снимок удовлетворяет правилам».

## 7. Читать коды причин

| Код | Значение |
| --- | --- |
| `allowed` | Все необходимые предпосылки и разрешения совпали |
| `company_unavailable` | Компания отсутствует или неактивна |
| `company_mismatch` | Компания объекта не соответствует области запроса |
| `project_unavailable` | Проект отсутствует или неактивен |
| `project_mismatch` | Идентификатор или проектная область не совпали |
| `employee_unavailable` | Нужный активный сотрудник не предоставлен |
| `agent_unavailable` | Нужный активный агент не предоставлен |
| `agent_employee_mismatch` | Агент связан с другим сотрудником |
| `delegation_unavailable` | Делегирование отсутствует или неактивно |
| `delegation_mismatch` | Делегирование связано с другим сотрудником или агентом |
| `action_not_delegated` | Действие не входит в делегирование агента |
| `document_unavailable` | Документ отсутствует или неактивен |
| `document_mismatch` | Предоставлен другой документ |
| `version_unavailable` | Версия отсутствует или неактивна |
| `version_mismatch` | Идентификатор версии или её связь с документом не совпали |
| `employee_permission_missing` | Нет подходящего активного права сотрудника |

Ошибочный тип объекта, не-кортеж разрешений или повторяющиеся идентификаторы
`Grant` отклоняются как некорректный ввод, через `TypeError` или `ValueError`.
Это отличается от корректного запроса, которому политика вернула отказ.
Такой ввод не становится положительным решением и пока не проходит через
HTTP-обработку или постоянную запись аудита.

## 8. Создать событие попытки проверки

```python
from datetime import datetime, timezone

event = make_audit_event(
    decision,
    occurred_at=datetime(2026, 10, 24, 12, 0, tzinfo=timezone.utc),
)
```

`make_audit_event()` копирует запрос и исход из решения в `AuditEvent`.
Текст документа, его заголовок и произвольное сообщение с секретами не
передаются в эту функцию. Время задаёт вызывающая сторона; функция не читает
часы. Нужен `datetime` с часовым поясом, затем значение нормализуется к UTC.
Время без часового пояса отклоняется, чтобы событие не было неоднозначным.

Одинаковые решение и время дают одинаковое событие. Можно проверить
разрешённую и отклонённую попытки одинаковым способом. Однако событие пока
не записано в файл или БД. Оно не доказывает, что чтение, изменение или
доставка ответа произошли. Атомарность бизнес-изменения и аудита появится
с транзакционным хранилищем на этапе 03.

## 9. Проверить работу

```bash
uv run --locked pytest tests/domain
uv run --locked pytest
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked python scripts/check_docs.py
uv lock --check --offline
git diff --check
```

Проверки моделей должны обнаруживать некорректный тип, пустой или длинный
идентификатор, неверное действие, изменяемое множество и несогласованное
решение. Проверки политики отдельно рассматривают разрешение, отсутствие
права, другую компанию или проект, неверную связь сотрудника с агентом,
неактивные объекты, отзыв делегирования и разделение `READ`/`WRITE`.
Проверки события рассматривают точный запрос, исход, неизменяемость и время.

Ожидаемый исход задаётся в тесте по сценарию. Его нельзя получать вызовом той
же проверяемой функции: иначе ошибочная политика сможет подтвердить сама себя.
Фактическое число тестов и результаты команд находятся в
[отчёте](VERIFICATION.md), отдельно от публикации и удалённого CI.

HTTP-контракт первого этапа сохраняется. `/health` отвечает как прежде,
`/memory` и `/agents` возвращают `404`. Офлайн-политика ещё не вызывается
из HTTP-запроса и не устанавливает личность внешнего клиента.

## Типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| Ошибка про `Action` | Используйте `Action.READ`, а не строку `"read"` |
| Ошибка про `frozenset` | Действия задаются `frozenset({Action.READ})` |
| Ошибка про `grants` | Передайте кортеж, для одного права — `(grant,)` |
| Нельзя изменить `active` присваиванием | Создайте новый объект через `replace()` и повторите проверку |
| Агенту делегировано действие, но получен отказ | Проверьте также право сотрудника на нужный документ |
| `WRITE` есть, но `READ` отклонён | Эти действия независимы; чтение должно быть разрешено явно |
| Версия выглядит подходящей, но получен отказ | Сверьте её ID, компанию и `document_id` с запросом |
| Время события отклонено | Нужен `datetime` с часовым поясом |
| После запуска demo нет файла истории | На этом этапе событие существует только в памяти |
