# Этап 09. Усиление выпуска

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 08](STAGE_08.md)

## Что меняется

На этапе 08 контейнерная лаборатория заработала, но с явными слабостями:
API подключался к PostgreSQL суперпользователем, пароль передавался через
переменную окружения, контейнеры могли писать в свою файловую систему, а
образы никто не проверял на известные уязвимости. Этап 09 закрывает эти
пункты, не меняя поведение API для агентов.

Решение: [ADR 0009](adr/0009-least-privilege-release.md). Это по-прежнему
локальная лаборатория на вымышленных данных, а не корпоративное развёртывание.

## Граница этапа

Реализованы роль БД с минимальными правами, секреты-файлы Docker вместо
переменных с паролями, контейнеры только для чтения без Linux capabilities,
образ БД без `gosu`, проверка этих свойств в сценарии и сканирование обоих
образов в CI. Не реализованы TLS, корпоративный вход, внешний менеджер
секретов, ротация паролей, плановые копии, оповещения и живая модель.

## 2. Роль БД с минимальными правами

Раньше учётная запись API была владельцем схемы и суперпользователем. Если бы
процесс API был скомпрометирован, он мог бы выдать себе права, переписать
версии или стереть аудит. Теперь API подключается как `agentic_app` — член
группы `agentic_memory_app`, у которой есть только нужное:

| Таблицы | Права группы |
| --- | --- |
| `projects`, `employees`, `agents`, `agent_credentials`, `delegations`, `documents`, `grants`, `sources`, `source_documents`, `alembic_version` | Только `SELECT` |
| `versions`, `write_requests` | `SELECT`, `INSERT` |
| `audit_events`, `context_requests`, `context_items`, `agent_runs`, `agent_run_searches`, `agent_run_citations` | Только `INSERT` |
| `companies` | `SELECT` и `UPDATE (name)` — только ради блокировки строки |
| `source_accounts`, `source_sync_runs` | Нет доступа |

Почему у `companies` есть `UPDATE (name)`: PostgreSQL разрешает
`SELECT … FOR UPDATE` только роли с правом изменения хотя бы одного столбца,
а блокировка строки компании — основа всех операций памяти. Чтобы это право
нельзя было использовать, триггер `companies_reject_memory_app_update`
отклоняет любое изменение `companies` участником группы с кодом
`insufficient_privilege` (`42501`). Владелец схемы и доверенная настройка
изменения по-прежнему выполняют.

Итог: под этой ролью нельзя изменить права, делегирование, токены, документы,
версии и историю, продлить подтверждение источника, прочитать аудит или
соответствия учётных записей источника, создать или удалить таблицу.
Синхронизация источника и учебные команды остаются доверенными операциями
владельца схемы.

Права задаёт миграция `0006_app_role`. Роли в PostgreSQL общие для всего
кластера, поэтому миграция создаёт группу, только если её ещё нет. Откат
снимает права и триггер в текущей базе, но не удаляет роль: её могут
использовать другие базы кластера. Тест сверяет права каждой таблицы
с таблицей выше и требует решения для каждой новой таблицы: новая миграция
обязана явно выдать (или не выдать) права, иначе тест упадёт.

## 3. Секреты-файлы

Пароль больше не передаётся через `POSTGRES_PASSWORD`. Переменная окружения
видна в `docker inspect` и в `/proc` процесса, а файл-секрет — нет. Команда
создаёт четыре файла:

```bash
uv run --locked python -m scripts.lab_secrets "$AGENTIC_SECRETS_DIR"
```

| Файл | Кто получает |
| --- | --- |
| `postgres_password` | `db`: пароль владельца схемы `agentic` |
| `app_db_password` | `db`: пароль `agentic_app`, читается скриптом создания ролей |
| `migrate_database_url` | `migrate`: адрес владельца через `DATABASE_URL_FILE` |
| `app_database_url` | `app`: адрес `agentic_app` через `APP_DATABASE_URL_FILE` |

Каждый сервис видит только свои файлы. Папка создаётся с правами `0700`,
файлы — `0644`: внутри контейнеров их читают пользователи `postgres` и `app`.
Существующие файлы команда не перезаписывает, потому что пароли фиксируются
при первом создании тома. Значения нигде не печатаются.

Без переменной `AGENTIC_SECRETS_DIR` Compose ищет файлы в `var/secrets`. На
macOS Docker Desktop может не получить доступ к репозиторию внутри защищённых
папок `Desktop`, `Documents` или `Downloads`: запуск остановится с ошибкой
`invalid mount config … operation not permitted`. Тогда держите секреты
в папке вне них:

```bash
export AGENTIC_SECRETS_DIR="$HOME/.agentic-lab-secrets"
uv run --locked python -m scripts.lab_secrets "$AGENTIC_SECRETS_DIR"
docker compose up --detach --wait
export DATABASE_URL="postgresql+psycopg://agentic:$(cat "$AGENTIC_SECRETS_DIR/postgres_password")@127.0.0.1:55436/agentic_lab"
uv run --locked python -m app.persistence_demo --setup
```

Скрипт создания ролей встроен в образ БД (`docker/postgres/Dockerfile`), а не
смонтирован из репозитория, по той же причине. Он выполняется один раз при
создании тома и читает пароль внутри `psql` из файла, а не из аргументов.
`docker compose down` работает и без файлов-секретов.

## 4. Контейнеры

| Свойство | `app` и `migrate` | `db` |
| --- | --- | --- |
| Пользователь | `app` (UID 10001) | `postgres` (UID 999) с самого старта |
| Корневая файловая система | Только чтение, `/tmp` — tmpfs | Только чтение; данные — в томе, `/tmp` и каталог сокета — tmpfs |
| Linux capabilities | Все сброшены | Все сброшены |
| `no-new-privileges` | Да | Да |
| Пароли в окружении | Нет, только путь к файлу | Нет, только путь к файлу |

Официальный образ PostgreSQL стартует от root и сбрасывает права утилитой
`gosu`. Сканер нашёл в её устаревшей среде Go 1 CRITICAL и 25 HIGH
уязвимостей с выпущенными исправлениями — это были все исправимые находки
образа БД. Наш образ БД запускается сразу от `postgres`, поэтому `gosu`
не нужен и удалён.

## 5. Сканирование образов

Задание CI `container-lab` после сценария сканирует `agentic-infrastructure:local`
и `agentic-infrastructure-db:local` образом `aquasec/trivy:0.75.0`,
закреплённым по digest (а не изменяемой меткой action). Сначала печатается
полный список HIGH и CRITICAL, затем отдельный запуск с `--ignore-unfixed
--exit-code 1` роняет задание, если есть HIGH или CRITICAL с уже выпущенным
исправлением. Уязвимости без исправления видны в журнале, но не блокируют.

Локально то же самое:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.75.0@sha256:af6acf9a6b85dfe389a1941505c0ce9efef52a4719635e1a962f022a3d855daa \
  image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 \
  agentic-infrastructure:local
```

База уязвимостей меняется каждый день. Задание может начать падать без
изменений кода, когда для пакета закреплённого базового образа выйдет
исправление. Это ожидаемый сигнал: обновите digest базового образа и
повторите проверки. Фактические числа — в [отчёте](VERIFICATION.md).

## 6. Что проверяет сценарий

`scripts/compose_lab.py` теперь создаёт секреты во временной папке вне
репозитория (`0700`) и удаляет её после прогона. Новый шаг проверки усиления
до учений смотрит `docker inspect` обоих контейнеров (пользователь, только
чтение, `cap_drop`, `no-new-privileges`, нет паролей в окружении), убеждается
по `pg_stat_activity`, что API подключён как `agentic_app`, и от имени этой роли
пытается расширить права, продлить подтверждение источника и стереть аудит —
каждая попытка должна получить `42501`. Если хотя бы одно условие не выполнено,
сценарий завершается с кодом `1`. Все прежние шаги этапа 08 сохраняются;
после восстановления тома скрипт ролей создаёт их заново с теми же паролями.

## 7. Назначение новых функций

| Функция / метод | Зачем нужна |
| --- | --- |
| `read_secret_file()` | Чтение однострочного секрета с проверкой размера и без вывода содержимого |
| `Settings.load_database_url_file()` | Адрес БД из файла; запрет двух источников сразу |
| `upgrade()` / `downgrade()` миграции 0006 | Права группы и триггер; откат без удаления общей роли |
| `LabSecrets.host_url()` | Loopback-адрес для учебных команд как владелец или как сервис |
| `write_secrets()` | Новые пароли и четыре файла без перезаписи |
| `lab_secrets.main()` | CLI создания папки секретов |
| `Lab.__init__()` | Секреты запуска во временной папке |
| `Lab.remove_secrets()` | Удаление папки секретов запуска |
| `_inspect()` | Данные `docker inspect` контейнера сервиса |
| `_locked_down()` | Пользователь, только чтение, без capabilities, `no-new-privileges` |
| `hardening_check()` | Усиление обоих контейнеров и запреты роли сервиса |

создают и удаляют временную роль входа. Результаты — в [отчёте](VERIFICATION.md).

## Типичные ошибки

| Симптом | Причина и решение |
| --- | --- |
| `invalid mount config … operation not permitted` | Docker Desktop не видит папку секретов; задайте `AGENTIC_SECRETS_DIR` вне `Desktop`/`Documents` |
| `secret files already exist` | Файлы уже созданы; используйте их или удалите вместе с томом |
| `migrate` или `app` не проходят аутентификацию | Секреты новее тома; верните прежние файлы или `docker compose down --volumes` |
| `permission denied` (`42501`) в API | Новой таблице не выданы права в миграции; добавьте решение и строку матрицы |
| Сканирование в CI упало без изменений кода | Вышло исправление для пакета базового образа; обновите digest |

## Ограничения

Роль сервиса по-прежнему видит все документы и токены-хэши своей базы: защиту
по компаниям обеспечивает приложение, а не построчная защита PostgreSQL. Секреты
— файлы на диске хоста, без ротации и внешнего хранилища. Сканер знает только
опубликованные уязвимости; в образах остаются HIGH без исправления. TLS,
корпоративный вход, плановые копии, оповещения и живая модель не реализованы.
