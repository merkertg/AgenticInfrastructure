# Этап 03. PostgreSQL, версии памяти и история операций

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 02](STAGE_02.md)

## Что меняется после этапа 02

Раньше проверка получала готовые Python-объекты и возвращала решение.
После завершения процесса объекты исчезали. Правило доступа уже можно было
проверить, но нельзя было повторно прочитать сохранённую версию документа
или доказать, что изменение и запись о нём появились вместе.

Теперь добавляем PostgreSQL. Сервисный Python-код загружает из БД текущие
объекты компании, проекта, сотрудника, агента, делегирования и прав. Для решения
он использует прежнюю функцию `evaluate_access()`. Разрешённое чтение возвращает
сохранённую версию, а запись добавляет новую версию существующего документа.
Результаты операций фиксируются в таблице аудита.

Например, в учебной компании Alpha есть финансовый документ с версией 1.
Разрешённый запрос читает именно эту версию. Запрос изменения с ожидаемым
номером 1 создаёт версию 2. Версия 1 сохраняется. Повтор того же запроса
не создаёт версию 3, а возвращает метаданные уже созданной версии 2.
Если обязательная запись аудита не проходит, изменение откатывается.

## Граница этапа

Реализованы подключение к PostgreSQL, миграции, хранение предметных объектов,
чтение версии, добавление новой версии, проверка текущих прав, идемпотентность
записи и транзакционный аудит. Сценарии выполняются доверенным Python-кодом
и на вымышленных данных. Фактические локальные и удалённые результаты
записаны отдельно в [отчёте](VERIFICATION.md).

HTTP-приложение по-прежнему предоставляет только `/health` и документацию API.
Переданный `employee_id` пока не доказывает личность вызывающего. Аутентификация
и маршруты памяти появятся на этапе 04. Нет поиска, загрузки произвольных
документов, управления правами через агента, модели или корпоративного источника.
Начальные документы и права создаются доверенной настройкой лаборатории.
Это не операция, доступная агенту.

## 2. Подготовить отдельную лабораторию PostgreSQL

Для основы HTTP и офлайн-демо БД не нужна. Для этого этапа нужна запущенная
PostgreSQL и отдельная учебная база. Следующие команды — пример новой локальной
лаборатории на macOS с уже установленной PostgreSQL 17. Они не используют
существующий домашний каталог данных PostgreSQL.

```bash
AGENTIC_PG_BIN=/opt/homebrew/opt/postgresql@17/bin
AGENTIC_PG_ROOT=$(mktemp -d /private/tmp/agentic-pg.XXXXXX)
"$AGENTIC_PG_BIN/initdb" -D "$AGENTIC_PG_ROOT/data" -U agentic -A trust --encoding=UTF8 --no-locale
LC_ALL=C "$AGENTIC_PG_BIN/pg_ctl" -D "$AGENTIC_PG_ROOT/data" -l "$AGENTIC_PG_ROOT/postgres.log" -o "-h 127.0.0.1 -p 55435 -k $AGENTIC_PG_ROOT" start -w
"$AGENTIC_PG_BIN/createdb" -h 127.0.0.1 -p 55435 -U agentic agentic_lab
"$AGENTIC_PG_BIN/createdb" -h 127.0.0.1 -p 55435 -U agentic agentic_test
```

`initdb` создаёт новый кластер — каталог файлов отдельного экземпляра PostgreSQL.
`pg_ctl` запускает этот экземпляр, а `-w` ждёт готовности сервера.
`LC_ALL=C` задаёт явную локаль процесса: без неё PostgreSQL на macOS может
остановиться при старте с сообщением `postmaster became multithreaded during startup`.
`createdb` создаёт две базы внутри него:
`agentic_lab` для демонстрации и `agentic_test` для проверок с очисткой данных.
Порт `55435` выбран для примера; если он занят, выберите другой и замените его
во всех последующих URL. Сохраните значение `AGENTIC_PG_ROOT`, пока работаете
с лабораторией.

Режим `trust` применяется только к этой временной локальной лаборатории
с вымышленными данными. Он не проверяет пароль. Настройка корпоративного
сервера и рабочих ролей не является результатом этого этапа.

Укажите соединение в терминале проекта:

```bash
export DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_lab'
export TEST_DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_test'
```

`postgresql+psycopg` задаёт СУБД и драйвер. Далее идут пользователь, адрес,
порт и имя базы. Приложение принимает PostgreSQL URL; SQLite не используется
как замена интеграционной проверке. Эти переменные задаются явно и отделены
от веб-настроек `APP_*`. Они не означают, что `/health` подключается к базе.
Не помещайте строку реального подключения в Git.

## 3. Применить миграцию

Из корня репозитория:

```bash
uv sync --locked
uv run --locked alembic upgrade head
```

`upgrade head` означает «применить ещё не выполненные миграции до последней».
При первом запуске создаются таблицы и запись Alembic о версии схемы.
При повторном запуске уже применённая миграция не выполняется заново.
Миграция меняет структуру БД; она не подменяет сохранённые документы
и не открывает доступ к HTTP API.

Новый пустой кластер и схема приложения — разные вещи: `createdb` создаёт базу,
а Alembic создаёт внутри неё нужные таблицы. Не заменяем миграции вызовом
`metadata.create_all()` в обычном запуске. История миграций должна оставаться
воспроизводимой после следующих изменений проекта.

`make_engine()` создаёт объект доступа к PostgreSQL без импорта веб-приложения.
Подключение происходит при выполнении операции. SQL-параметры не выводятся
через автоматическое логирование engine. `migrate()` позволяет применить
миграции из Python, используя ту же схему Alembic.

Механизм транзакций описан в
[документации SQLAlchemy](https://docs.sqlalchemy.org/en/21/core/connections.html#using-transactions),
а назначение окружения миграции — в
[руководстве Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html).

## 4. Понять, что хранится

| Таблица | Смысл |
| --- | --- |
| `companies` | Компании и их активность |
| `projects` | Проекты внутри компании |
| `employees` | Сотрудники компании |
| `agents` | Регистрация агента за сотрудником |
| `delegations` | Действия, делегированные агенту в проекте |
| `documents` | Документ, компания, проект и заголовок |
| `versions` | Неизменяемые через API редакции документа с текстом и источником |
| `grants` | Права сотрудника на документ |
| `audit_events` | Метаданные попытки, решения и результата операции |
| `write_requests` | Результаты выполненных записей для обработки повтора |

У большинства объектов ключ включает `company_id`. Поэтому одинаковое локальное
имя объекта в другой компании не должно случайно соединиться с первой компанией.
Составной внешний ключ проверяет несколько полей вместе. Например, разрешение
связано с документом именно его компании и проекта; делегирование связано
с зарегистрированным агентом и его сотрудником.

Внешний ключ не устанавливает личность пользователя. Он проверяет целостность
записей в БД. Правило доступа всё равно применяется к каждому обращению.

Версии получают отдельные идентификаторы и последовательные номера внутри
документа. Новая редакция добавляется новой строкой. Операции памяти не предлагают
перезапись текста старой версии. Это помогает сохранить старую ссылку на источник.
Владелец БД с прямым SQL-доступом технически обладает более широкими полномочиями;
этот слой не объявляется защитой от администратора PostgreSQL.

## 5. Проследить разрешённое чтение

```text
AccessRequest с действием READ
        ↓
начало транзакции и блокировка компании
        ↓
загрузка текущих объектов и разрешений из PostgreSQL
        ↓
evaluate_access()
        ↓
запись audit_events: разрешение/отказ и результат
        ↓
успешный commit
        ↓
возврат версии только при разрешённом чтении
```

`MemoryStore.read_version()` принимает запрос и время попытки с часовым поясом.
Он проверяет сохранённые связи и текущие права, а не готовое положительное
решение из предыдущего процесса. Если доступ запрещён, результат не содержит
текст версии. Запись отказа не требует существования чужого или неизвестного
объекта: это важно, чтобы сохранять попытку обращения к отсутствующему ID.

Аудит содержит идентификаторы сотрудника, агента, области и цели, действие,
код решения, результат операции и время. Текст документа, источник и секреты
в него не копируются. Время нормализуется в UTC.

Если вставка аудита или commit завершается ошибкой, метод не возвращает
успешный результат с документом. При недоступной БД невозможно гарантировать
и сохранение самого отказа. Это ограничение записываем явно.

## 6. Проследить добавление версии

`MemoryStore.write_version()` получает запрос с действием `WRITE`, новый объект
`DocumentVersion`, ожидаемый номер текущей редакции и время попытки.
`request.version_id` указывает на базовую версию, от которой выполняется изменение.

Порядок работы:

1. Начать транзакцию, заблокировать строку компании и загрузить текущие права.
2. Проверить действие `WRITE` через прежнюю предметную политику.
3. Проверить, не был ли этот запрос уже выполнен с теми же данными.
4. Проверить базовую редакцию, ожидаемый текущий номер и новую версию.
5. Добавить новую строку версии, аудит и результат запроса для повтора.
6. Выполнить commit и вернуть метаданные новой версии.

Пример: база содержит версию 1. Вы передали ожидаемый номер 1 и новую версию 2.
После успеха обе версии сохранены. Если другой запрос уже создал версию 2,
новый запрос с ожиданием 1 получает `version_conflict`. Он не затирает чужое
изменение. Коллизия нового идентификатора версии также является конфликтом.

Проверка ожидаемого номера — способ обнаружить устаревшее изменение.
Блокировка строки компании удерживается до конца транзакции и упорядочивает
операции текущего адаптера. Она описана в
[документации PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html).
Это простая блокировка на уровне компании: операции разных документов одной
компании тоже могут ждать друг друга. Не выдаём её за подтверждённую высокую
производительность. Прямые административные SQL-изменения должны отдельно
учитывать эту границу; они не являются операциями агента.

Адаптер явно использует уровень изоляции PostgreSQL `READ COMMITTED`, в том числе
для переданного извне engine. После ожидания блокировки следующие запросы
должны увидеть уже зафиксированную версию и запись идемпотентности предыдущей
транзакции. Снимок, удерживаемый более строгим уровнем изоляции до конца
транзакции, не соответствует этому алгоритму повторной проверки.

Право записи не даёт право чтения. Поэтому успешная запись возвращает
идентификатор и номер результата, а не тело документа. Текст новой версии
передаёт вызывающий код; для отдельного чтения требуется отдельное разрешение.

## 7. Что означает идемпотентность

После отправки изменения клиент может не получить ответ и повторить запрос.
Без отдельного правила такой повтор мог бы создать ещё одну редакцию.

В `write_requests` ключ состоит из компании, сотрудника, агента и `request_id`.
Рядом хранится отпечаток содержимого запроса и метаданные созданной версии.
В отпечаток включены данные операции и новой версии; время очередной попытки
не включено, поскольку повтор может прийти позже.

- Тот же ключ и те же данные: возвращается прежний результат с признаком
  повтора, новая версия не создаётся.
- Тот же ключ, но другой текст, цель или другие данные: `idempotency_conflict`.
- Право сотрудника или делегирование отозвано: отказ при новой проверке,
  даже если этот ключ раньше завершился успешно.

Перед поиском результата повтора снова проверяются действующие права.
Сохранённый результат не является бессрочным разрешением. Каждая попытка,
дошедшая до проверки прав, включая повтор и конфликт, получает собственную
запись аудита, когда её можно сохранить. Ошибки типа запроса, действия, времени
или формы новой версии отклоняются до начала транзакции и не записываются
как бизнес-операция. Полный текст не помещается в таблицу идемпотентности: он уже хранится
в конкретной версии документа.

## 8. Почему транзакция объединяет изменение и аудит

Транзакция — группа операций БД с общим исходом. При `commit` изменения
фиксируются, при `rollback` они отменяются. Для добавления версии вместе
фиксируются три вещи: новая версия, запись аудита и результат запроса.

Если версия добавилась, но обязательный аудит упал, транзакция откатывает
и версию, и запись идемпотентности. Поэтому повтор не должен найти «успех»,
который на самом деле не был зафиксирован. У чтения нет новой версии,
но успешная выдача результата также зависит от записи аудита и commit.

Событие этапа 02 было только неизменяемым Python-объектом попытки авторизации.
Теперь таблица дополнительно хранит результат операции: `read`, `written`,
`denied`, `version_conflict` или `idempotency_conflict`. Положительное решение
авторизации ещё не означает успешную запись: после него возможен конфликт.
Запись о чтении не доказывает, что клиент физически получил ответ по сети.

## 9. Запустить сценарий с БД

После миграции один раз создайте вымышленные начальные записи в новой
лабораторной БД, затем выполните сценарий:

```bash
uv run --locked python -m app.persistence_demo --setup
uv run --locked python -m app.persistence_demo
```

`validate_lab_url()` принимает только локальный PostgreSQL URL с именем БД,
оканчивающимся на `_lab`, без дополнительных параметров URL. `seed_lab()`
создаёт компанию Alpha, финансовый и инженерный проекты, сотрудников и агентов,
делегирования, финансовый документ `policy` с версией `policy-v1` и право
финансового сотрудника на чтение и запись. Это доверенная настройка лаборатории.
Она отклоняет повторную загрузку уже заполненного набора компаний;
`--setup` не является командой сброса БД.

`run_demo()` выполняет семь операций. Первый запуск после настройки должен
показать следующие результаты:

| `case` | `outcome` | Пояснение |
| --- | --- | --- |
| `read_v1` | `read` | Разрешено чтение версии `policy-v1` |
| `append_v2` | `written` | Создана `policy-v2`, `replayed=false` |
| `retry_v2` | `written` | Возвращена та же версия, `replayed=true` |
| `read_v2` | `read` | Разрешено чтение сохранённой версии 2 |
| `denied_engineer` | `denied` | Финансовый документ не относится к инженерному проекту |
| `stale_write` | `version_conflict` | Уже существует более новая редакция |
| `changed_retry` | `idempotency_conflict` | Изменён текст под прежним ключом запроса |

`main()` печатает JSON с полями `case`, `outcome`, `allowed`, `reason`,
`version_id`, `number`, `replayed`. Текст документа в вывод не попадает.
Для конфликтов `allowed` может быть `true`: права прошли проверку, а сама
запись не выполнена из-за конфликта. Время попыток задано фиксированным
значением `2026-10-24T00:00:00+00:00` для учебного сценария.

Повторный запуск без `--setup` использует ту же БД. Поскольку успешная запись
с этим ключом уже сохранена, `append_v2` теперь тоже имеет `replayed=true`.
Новая версия не появляется, а аудит получает новые попытки. Точные фактически
выполненные проверки сохранения и перезапуска записываются в отчёте.

В собственной лаборатории можно посмотреть метаданные без вывода текста:

```bash
"$AGENTIC_PG_BIN/psql" -h 127.0.0.1 -p 55435 -U agentic -d agentic_lab -c "SELECT company_id, document_id, number, id FROM versions ORDER BY company_id, document_id, number;"
"$AGENTIC_PG_BIN/psql" -h 127.0.0.1 -p 55435 -U agentic -d agentic_lab -c "SELECT result, replayed, count(*) FROM audit_events GROUP BY result, replayed ORDER BY result, replayed;"
"$AGENTIC_PG_BIN/psql" -h 127.0.0.1 -p 55435 -U agentic -d agentic_lab -c "SELECT count(*) FROM write_requests;"
```

Первый запрос показывает версии и их принадлежность. Второй группирует попытки
по исходу и признаку повтора. Третий считает сохранённые успешные записи
для идемпотентности. После первого полного сценария ожидаются две версии,
семь записей аудита и один результат записи. После очередного запуска число
попыток растёт, а версии и результат записи не дублируются. Здесь используется
имя отдельной учебной базы, а не подключение к корпоративному хранилищу.

Офлайн-демо предыдущего этапа остаётся доступным отдельно:

```bash
uv run --locked python -m app.demo
```

Первая команда требует PostgreSQL, вторая работает без сети и БД.
Ни одна не открывает HTTP-маршруты памяти и не подтверждает личность сотрудника.

## 10. Выполнить проверки

Без запущенной БД:

```bash
uv run --locked pytest -m 'not postgres'
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts migrations
uv run --locked python scripts/check_docs.py
uv lock --check --offline
git diff --check
```

С отдельной тестовой базой:

```bash
export TEST_DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_test'
uv run --locked pytest -m postgres
```

Интеграционные тесты перед очисткой проверяют тип соединения, локальный адрес
и суффикс `_test`. Они не должны брать `DATABASE_URL` вместо тестового URL.
Если переменная отсутствует, обычный локальный запуск пропускает проверки БД.
Это состояние `skipped`, а не успешная проверка PostgreSQL. Если URL задан,
ошибка соединения должна приводить к ошибке теста.

Проверки охватывают миграции, сохранение, старые версии, повтор запроса,
конфликт изменения, отзыв прав, границы компании и проекта и откат при ошибке
аудита. Отдельные конкурентные запросы проверяют, что два одинаковых повтора
не создают две версии. Нужна настоящая PostgreSQL: SQLite и моки не доказывают
эту часть поведения. Число выполненных тестов, версия сервера и факт проверки
перезапуска фиксируются только после наблюдения результата в отчёте.

## 11. Остановить собственную лабораторию

Если вы запускали временный экземпляр из шага 2:

```bash
"$AGENTIC_PG_BIN/pg_ctl" -D "$AGENTIC_PG_ROOT/data" stop
```

Остановка сервера не удаляет файлы базы. Повторный запуск того же каталога
той же командой `LC_ALL=C ... pg_ctl ... start -w` из шага 2 должен сохранить
зафиксированные данные. Проверка этой возможности отличается
от создания нового Python engine; фактический перезапуск сервера учитывается
отдельно в отчёте. Не останавливайте чужой или общий экземпляр PostgreSQL.

## Типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| Нет `DATABASE_URL` | Задайте URL явно в текущем терминале |
| `connection refused` | Сервер, адрес и порт; миграция не запускает PostgreSQL |
| `postmaster became multithreaded during startup` | Запустите `pg_ctl` с `LC_ALL=C`, как в шаге 2 |
| Таблица не существует | Выполнена ли миграция именно в указанной базе |
| PostgreSQL-тесты пропущены | Задан ли отдельный `TEST_DATABASE_URL` |
| Тесты отвергают URL | PostgreSQL, локальный адрес и база с суффиксом `_test` |
| `version_conflict` | Изменение основано на текущем номере версии? |
| `idempotency_conflict` | Не изменён ли payload под прежним `request_id`? |
| Старый запрос после отзыва отклонён | Это ожидается: права проверяются заново |
| Ошибка вставки аудита | Успех не возвращается; изменение должно откатиться |
| `/memory` возвращает `404` | HTTP-доступ к памяти относится к следующему этапу |
