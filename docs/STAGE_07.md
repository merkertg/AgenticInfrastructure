# Этап 07. Один источник документов для чтения

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 06](STAGE_06.md)

## Что меняется

Раньше оператор загружал вымышленные `.txt`-файлы. Теперь отдельный источник
Handbook отдаёт список документов, редакции, читателей и текст по HTTP.
Синхронизация переносит их в память: изменение текста создаёт версию,
исчезновение из полного списка отключает документ, отзыв читателя убирает
его право. Агент продолжает пользоваться теми же маршрутами памяти,
поиска и ответов; учётные данные источника он не получает.

Это **адаптер вымышленного контракта `handbook-http-v1` и отдельная
HTTP-лаборатория**. Настоящий корпоративный сервис, его пользователи и права
не подключены и не проверены. Решение: [ADR 0007](adr/0007-read-only-source-sync.md).

## 1. Границы доверия

Оператор один раз регистрирует адрес, пространство источника, компанию,
проект, префикс документов и таблицу соответствий пользователей. Например,
`u-fin → fin-user` означает, что внешний пользователь соответствует уже
существующему сотруднику. Сам документ не может создать такое соответствие.
Группы и неизвестные пользователи прав не дают. Сотрудник по-прежнему должен
быть активен, а его агент — иметь текущее делегирование в нужном проекте.

Адаптер строит адреса сам и использует только GET. Он не следует
перенаправлениям, не использует proxy-переменные окружения и не берёт URL
из ответа источника. HTTPS проверяет сертификат; обычный HTTP разрешён только
для loopback-лаборатории. Токен передаётся через `SOURCE_TOKEN`, используется
в `Authorization` только для зарегистрированного адреса и не сохраняется
в БД, истории или модели. Для реального сервиса оператор должен отдельно
выдать токен с правами только чтения: клиент с GET не доказывает права токена
на стороне сервиса.

## 2. Контракт и ограничения

Источник отвечает на два запроса:

```text
GET /v1/spaces/{space}/documents?cursor=...
GET /v1/spaces/{space}/documents/{id}/content?revision=...
```

Первая страница запрашивается без `cursor`. Пример её тела:

```json
{"documents":[{"id":"travel-desk","title":"Travel desk rules","revision":"r1",
 "readers":[{"kind":"user","id":"u-fin"}]}],"next_cursor":null}
```

Страница содержит ровно `documents` и `next_cursor`; документ — `id`,
`title`, `revision`, `readers`; читатель — `kind` и `id`. Повтор ключа JSON,
лишнее поле, `NaN`, неправильный UTF-8 или идентификатор отклоняют страницу.
Ответ текста — `text/plain`, список — `application/json`.

| Ограничение | Значение |
| --- | --- |
| Страницы одного списка | до 20 |
| Документы страницы / полного снимка | до 100 / 200 |
| Размер страницы | до 262 144 байт |
| Читатели документа | до 100 |
| Соответствия пользователей | до 1 000 |
| Текст | до 64 КиБ и 20 000 символов, правила этапа 05 |
| Время запроса / сбора снимка | до 5 / 60 секунд |
| Окно подтверждения доступа | 60–86 400 секунд |
| Документы проекта, включая неактивные | до 500 |

Ожидание сетевого результата ограничено по общим часам: DNS, соединение,
заголовки и тело выполняются в отдельном daemon-потоке. При таймауте клиент
возвращает код и по возможности закрывает сокет; позднее завершение соединения
после отмены не отправляет запрос с токеном. Системный DNS может оставить
поток работающим, поэтому на процесс допускаются только четыре таких потока.
Лимит сбора проверяется до и после каждого запроса и перед возвратом снимка.
Источник должен менять `revision` при изменении
текста: неизменённая редакция повторно не загружается. Согласованность
страниц одного снимка — условие контракта; отдельного идентификатора полного
снимка и ETag пока нет.

## 3. Почему сначала нужен полный список

Удаление определяется отсутствием документа в полном списке. Если пропала
вторая страница, это не означает, что все её документы удалены. Поэтому
сначала собирается весь список с проверкой лимитов, повторённых ID и циклов
курсора. Затем загружаются тексты новых и изменённых редакций.

Сетевые операции идут без транзакции и блокировки компании. После них
синхронизация открывает транзакцию, блокирует компанию, повторно читает
настройки источника, состояние документов и активные соответствия сотрудников.
Чистая функция `plan_sync()` строит план; адаптер одной транзакцией применяет
версии, активность документов, права, подтверждение и запись запуска.
Ошибка обязательной истории откатывает изменения.

Если другая синхронизация уже применила более новый снимок либо изменились
настройки, старый результат получает `superseded`. Конфликт ID с существующим
документом или превышение лимита проекта также отклоняют весь снимок.

| Ситуация | Результат |
| --- | --- |
| Новый документ и допустимый текст | Новый документ и версия |
| Новая редакция с другим текстом | Следующая версия, старая сохраняется |
| Новая редакция с тем же нормализованным текстом | Новая версия не создаётся |
| Неизменённая редакция | Текст не загружается; права и подтверждение обновляются |
| Документ отсутствует в полном списке | Документ отключается, активные права отзываются |
| Неверный текст одного документа | `withheld`, документ недоступен, его права отозваны; остальные изменения применяются |
| Ошибка списка, сети или получения текста | Ничего из снимка не применяется |
| Ранее удалённый документ снова появился | Доступность восстанавливается по текущим читателям; при прежнем тексте новая версия не нужна |

Источник владеет правами своих документов: посторонние активные grant-записи,
включая ручные, отключаются при сверке. Его собственные grant-записи содержат
только `read`. Кроме этого, хранилище отдельно запрещает `write` на любой
синхронизированный документ, даже если администратор вручную выдал право записи.

## 4. Что происходит при недоступности и устаревании

Успешный полный снимок устанавливает `confirmed_at` во **время начала** запуска.
Окно включает время сетевой загрузки. Ошибка не передвигает это время вперёд.
До `confirmed_until` прежний снимок ещё может использоваться. В момент
истечения срока и позже чтение блокируется до следующего успешного снимка.
Это явная задержка применения внешнего отзыва; мгновенная проверка прав
на источнике при каждом чтении не реализована.

SQL исключает неподтверждённые источники до загрузки текста и подсчёта BM25.
Дополнительная проверка защищает прямое чтение версии, итоговые фрагменты
и ссылки ответа агента. Истёкшее подтверждение не делает весь проект
недоступным: поиск может вернуть обычные разрешённые документы проекта.
Отказ чтения версии остаётся единым HTTP `404`, а поиск без подходящих
документов возвращает `no_authorized_evidence`. В бизнес-аудите причина
записывается как `source_unconfirmed`; запрет записи — `source_read_only`.

Версии и ссылки истории сохраняются. Однако знание старого `version_id`
не обходит текущий отзыв, отключение документа или истёкший срок источника.
Индекса и кэша результатов нет; фрагменты строятся в текущем запросе.
Уже выданный клиенту текст отозвать технически невозможно.

## 5. Воспроизвести лабораторию

Нужна локальная PostgreSQL из [этапа 03](STAGE_03.md), отдельная новая база
`agentic_stage07_lab` и зависимости `uv sync --locked`. Учебные CLI принимают
только явный `DATABASE_URL` к loopback-БД с окончанием `_lab`, без query options.
`.env` для них не загружается.

В терминале источника:

```bash
"$AGENTIC_PG_BIN/createdb" -h 127.0.0.1 -p 55435 -U agentic agentic_stage07_lab
export DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_stage07_lab'
uv run --locked python -m app.persistence_demo --setup
export SOURCE_TOKEN="$(openssl rand -hex 24)"
uv run --locked python -m app.source_lab fixtures/source/handbook-1.json --port 8105
```

Во втором терминале установите тот же `DATABASE_URL` и тот же временный
`SOURCE_TOKEN`. Не сохраняйте токен в файле или Git. Затем:

```bash
uv run --locked python -m app.source_sync register handbook --project finance \
  --base-url http://127.0.0.1:8105 --space alpha-handbook --prefix hb- \
  --max-age 900 --account u-fin=fin-user --account u-eng=eng-user
uv run --locked python -m app.source_sync run handbook
uv run --locked python -m app.source_sync status handbook
uv run --locked python -m app.source_sync run handbook
```

`register` выполняется один раз. Первый снимок содержит четыре документа.
Финансовому сотруднику доступны `hb-travel-desk`, `hb-office-access` и
`hb-vendor-review`; `hb-partner-note` не имеет разрешённого читателя.
Группа `g-everyone` игнорируется. `u-eng` соответствует `eng-user`, но это
не выдаёт `eng-agent` делегирование в `finance`. Повтор читает список и права,
не создаёт дубликаты версий и не загружает неизменённый текст.

Чтобы выполнить поиск, выдайте токен агента и запустите API:

```bash
uv run --locked python -m app.credential_lab fin-agent
export FIN_TOKEN='aik1_...'
export APP_DATABASE_URL="$DATABASE_URL"
uv run --locked uvicorn app.main:app --host 127.0.0.1 --port 8005
```

В ещё одном терминале с `FIN_TOKEN`:

```bash
curl -s -X POST -H "Authorization: Bearer $FIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"train tickets","max_items":3}' \
  http://127.0.0.1:8005/memory/projects/finance/context
```

Ссылка указывает на `hb-travel-desk`, редакцию памяти 1 и источник
`handbook:travel-desk@r1`. Тот же маршрут `/answers` принимает вопрос
`When are train tickets booked?` и использует офлайн-провайдер этапа 06.

Остановите источник через `Ctrl+C` и запустите второе состояние с тем же токеном:

```bash
uv run --locked python -m app.source_lab fixtures/source/handbook-2.json --port 8105
```

Снова выполните `run handbook`. Теперь:

- `hb-travel-desk` имеет вторую версию: билеты бронируют за три дня;
- `fin-user` лишился `hb-office-access`: поиск `visitor badges` больше его не выдаёт;
- `hb-vendor-review` удалён: старую версию нельзя прочитать;
- `hb-budget-draft` удержан с причиной `control_characters`;
- `hb-partner-note` по-прежнему не имеет сопоставленного читателя.

Повторите запуск: новых версий быть не должно. Для восстановления верните
первое состояние и синхронизируйте его: доступ определяется его текущим списком
читателей. Это новое состояние источника, а не разрешение переиспользовать
старый ответ приложения.

Затем остановите источник и выполните `run handbook`: команда завершится
с кодом `1`, а `status handbook` покажет ошибку последнего запуска и прежний
`confirmed_at`. После `confirmed_until` синхронизированные документы не
попадают в поиск, а чтение их версий отклоняется. Чтобы не ждать 15 минут,
повторите упражнение в новой независимой лаборатории с `--max-age 60`.
Успешный запуск источника и синхронизации подтверждает доступ снова.

## 6. Состояние и история

| Таблица | Назначение |
| --- | --- |
| `sources` | Доверенные настройки, активность, время подтверждения |
| `source_accounts` | Явные соответствия внешнего пользователя сотруднику и их активность |
| `source_documents` | Внешний ID, документ памяти, последняя импортированная редакция, SHA-256 текста, состояние и код удержания |
| `source_sync_runs` | Времена, исход, код ошибки и счётчики запуска |

Текст хранится в обычных версиях памяти. История синхронизации не содержит
тел документов, URL, имён и токенов. Команда `status` предназначена для
доверенного оператора: она выдаёт срок подтверждения, количество документов
в каждом состоянии, до 50 внешних ID с кодом удержания и последний запуск.
`run` возвращает `0` при применении снимка и `1` при ожидаемой ошибке
синхронизации; ошибка параметров CLI даёт `2`. Ошибка БД не маскируется
успешным отчётом.

Миграция `0005_source_sync` добавляет четыре таблицы и связи компании/проекта.
При downgrade синхронизированные документы и их права сначала отключаются
под блокировками компаний, затем удаляются метаданные источников. Старые
тексты версий сохраняются недоступными. Откат схемы не восстанавливает
доступность и не является процедурой удаления корпоративных данных. Повторный
upgrade не восстанавливает принадлежность этих документов источнику: для
дальнейшего импорта потребуется доверенная подготовка.

| `source_lab.main()` | Запуск вымышленного источника с токеном из окружения |
| `upgrade()` / `downgrade()` миграции 0005 | Создание таблиц; безопасное отключение данных перед удалением метаданных |

Существующие `_decision()` хранилища и `authorized_versions()` поиска теперь
учитывают проверку источника. Разбор аргументов инструмента модели использует
общий `loads_strict()` с прежним строгим контрактом.

## 8. Проверить результат

```bash
uv sync --locked
uv run --locked pytest -m 'not postgres'
export TEST_DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_test'
uv run --locked pytest -m postgres
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts migrations
uv run --locked python scripts/check_docs.py
uv lock --check --offline
git diff --check
```

`TEST_DATABASE_URL` должен явно указывать на отдельную локальную одноразовую
БД `_test`, без параметров URL; тесты сбрасывают её таблицы. Отсутствие URL
пропускает PostgreSQL-тесты и не подтверждает работу хранения.

Тесты используют фиктивные клиенты, вымышленные JSON, loopback-сервер и
отдельный PostgreSQL. Они проверяют загрузку, повтор, изменения, удаление,
восстановление, читателей, read-only, срок подтверждения, фильтрацию до
ранжирования, итоговые ответы, сбой истории и конкурирующие снимки.
Фактические результаты, публикация и CI записываются в
[отчёт](VERIFICATION.md); команды в этом разделе сами по себе не означают
успех проверки. Публикация этапа 07 и её CI записаны в отчёте.
