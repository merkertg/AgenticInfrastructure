# Этап 04. Подтверждённая личность агента и HTTP API памяти

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 03](STAGE_03.md)

## Что меняется после этапа 03

На этапе 03 доверенный Python-код сам передавал `company_id`, `employee_id`
и `agent_id`. Хранилище проверяло права, но не могло знать, кто на самом деле
вызвал операцию. Поэтому память не открывалась по HTTP: любой клиент мог бы
написать в запросе чужой `employee_id`.

Теперь сервер сам определяет вызывающего. Агент предъявляет секретный токен
в заголовке `Authorization: Bearer ...`. Сервер находит в PostgreSQL запись
этого токена и узнаёт компанию, агента и сотрудника, за которым агент
зарегистрирован. Идентификаторы из пути, query-параметров, тела или других
заголовков не выбирают сотрудника.

Пример. Финансовый помощник `fin-agent` с токеном читает версию `policy-v1`
и получает `200` с текстом. Инженерный помощник со своим токеном запрашивает
тот же адрес и получает `404`: его делегирование относится к другому проекту.
Даже заголовок `X-Employee-ID: fin-user` ничего не меняет — сервер его не читает.
Запрос без токена получает `401`.

## Граница этапа

Реализованы учётные данные агентов, их хранение в виде хеша, проверка
при каждом запросе, повторная проверка внутри транзакции и два HTTP-маршрута:
чтение версии и добавление следующей версии. Разрешённый сценарий проходит
через HTTP, проверку токена, политику доступа, PostgreSQL и аудит.

Это учебный механизм, а не корпоративный SSO. Сотрудник не входит в систему
интерактивно: его полномочия задают доверенные записи регистрации агента,
делегирования и прав, созданные настройкой лаборатории. Токены выпускает
привилегированная команда лаборатории, а не агент. Нет поиска, загрузки новых
документов, управления правами по HTTP, ограничения частоты запросов,
модели и корпоративного источника. Решение и альтернативы описаны в
[ADR 0004](adr/0004-agent-credentials-memory-api.md).

## 2. Как сервер узнаёт, кто обращается

**Bearer-токен** — секретная строка, которую клиент передаёт в заголовке
`Authorization`. Слово *bearer* означает «предъявитель»: кто знает строку,
тот и проходит проверку. Поэтому токен — такой же секрет, как пароль.

```text
Authorization: Bearer aik1_<43 случайных символа>
        ↓
SHA-256 от токена → поиск в agent_credentials
        ↓
активен ли токен и не истёк ли срок
        ↓
Principal(company_id, employee_id, agent_id, credential_id)
        ↓
AccessRequest строится из Principal и пути запроса
```

`aik1_` — префикс формата. После него 43 символа из
`secrets.token_urlsafe(32)`: около 256 бит случайности. Подобрать такой токен
перебором нереально. Если строка не соответствует формату, сервер отклоняет её
сразу, не обращаясь к БД.

Сотрудник берётся из записи регистрации агента, к которой привязан токен.
Агент не может представиться другим сотрудником: такой привязки нет в БД.
Права агента — пересечение прав сотрудника на документ и делегирования
агенту в проекте. Поэтому агент никогда не получает больше, чем сотрудник.

## 3. Как хранятся учётные данные

| Поле `agent_credentials` | Смысл |
| --- | --- |
| `company_id`, `id` | Ключ учётных данных внутри компании |
| `agent_id`, `employee_id` | Регистрация агента; составной внешний ключ к `agents` |
| `token_hash` | SHA-256 токена, 64 шестнадцатеричных символа, уникален |
| `issued_at`, `expires_at` | Время выпуска и обязательный срок действия |
| `active` | `false` означает отзыв |

Сам токен в БД не хранится. Если кто-то прочитает таблицу, он увидит только
хеш, из которого токен восстановить нельзя. Для паролей людей нужна медленная
функция хеширования, потому что пароли угадываемы. Здесь токен случайный,
поэтому достаточно SHA-256.

Внешний ключ `(company_id, agent_id, employee_id)` ссылается на регистрацию
агента. Запись, которая связывает агента с чужим сотрудником, PostgreSQL
не примет. Миграция `0002` также добавляет в `audit_events` поле
`credential_id`: по нему видно, какими учётными данными выполнена операция.
У вызовов доверенного Python-кода из этапа 03 это поле пустое.

## 4. Подготовить лабораторию

Нужна запущенная PostgreSQL из [шага 2 этапа 03](STAGE_03.md). Создайте новую
базу и примените миграции вместе с начальными данными:

```bash
"$AGENTIC_PG_BIN/createdb" -h 127.0.0.1 -p 55435 -U agentic agentic_stage04_lab
export DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_stage04_lab'
uv run --locked python -m app.persistence_demo --setup
```

`--setup` применяет обе миграции до `0002_agent_credentials` и создаёт
вымышленную компанию Alpha. Если вы продолжаете с базой из этапа 03, вместо
нового `--setup` выполните `uv run --locked alembic upgrade head`.

Выпустите токены двум агентам:

```bash
uv run --locked python -m app.credential_lab fin-agent
uv run --locked python -m app.credential_lab eng-agent --hours 2
```

Команда печатает JSON с `credential_id`, `agent_id`, `expires_at` и `token`.
Токен показывается **один раз**: в БД остаётся только хеш. Срок действия
по умолчанию — 8 часов, допустимо от 1 до 168. Команда принимает только
локальную базу с именем на `_lab`.

Сохраните токены в переменные текущего терминала:

```bash
export FIN_TOKEN='aik1_...'
export ENG_TOKEN='aik1_...'
```

Не записывайте токены в Git, `.env.example`, отчёты или журналы. Это секреты,
пусть и учебные.

## 5. Запустить API с базой

Веб-приложение подключается к БД только через явную переменную
`APP_DATABASE_URL`. `DATABASE_URL` используют миграции и команды лаборатории;
веб-сервер её не читает.

```bash
export APP_DATABASE_URL="$DATABASE_URL"
uv run --locked uvicorn app.main:app --host 127.0.0.1 --port 8005
```

Создание приложения проверяет драйвер в URL, но не открывает соединение.
`/health` по-прежнему не обращается к БД и отвечает `200`, даже если PostgreSQL
недоступна. Если `APP_DATABASE_URL` не задан, маршруты памяти отвечают `503`
с `memory storage is not configured`.

Сервер слушает только `127.0.0.1`. Bearer-токен передаётся открытым текстом,
поэтому вне локальной машины нужен TLS (HTTPS). Здесь он не настраивается.

## 6. Прочитать версию через HTTP

```bash
curl -i -H "Authorization: Bearer $FIN_TOKEN" \
  http://127.0.0.1:8005/memory/projects/finance/documents/policy/versions/policy-v1
```

Ответ `200`:

```json
{"document_id":"policy","version_id":"policy-v1","number":1,"source":"fixture:policy","content":"Fictional revision one."}
```

Заголовок `Cache-Control: no-store` просит браузеры и прокси не сохранять
ответ. Текст документа не должен оставаться в промежуточных кэшах.

Путь запроса проходит так:

```text
GET /memory/projects/{project}/documents/{document}/versions/{version}
        ↓
authenticated_caller(): токен → Principal, время сервера
        ↓
MemoryStore.read_version(request, credential_id=...)
        ↓
транзакция, блокировка компании, повторная проверка токена
        ↓
evaluate_access() по текущим записям БД
        ↓
аудит → commit → 200 с версией или 404 без текста
```

Идентификатор запроса чтения генерирует сервер (`uuid4`). Время операции
тоже берёт сервер, а не клиент.

## 7. Как выглядят отказы

| Ситуация | Ответ | Записан ли аудит |
| --- | --- | --- |
| Нет заголовка, схема не `Bearer`, неверная форма | `401` | Нет: вызывающий не установлен |
| Неизвестный, отозванный или истёкший токен | `401` | Нет |
| Чужая компания, другой проект, нет делегирования или права | `404` | Да, с причиной |
| Документ или версия не существуют | `404` | Да |
| Токен отозван после проверки, но до операции | `404` | Да, `credential_unavailable` |
| Ошибка БД или обязательного аудита | `503` | Не гарантирован |

Все ответы `401` одинаковы: `{"detail":"invalid or missing credentials"}`
и заголовок `WWW-Authenticate: Bearer`. Клиент не узнаёт, был ли токен
неизвестен, отозван или истёк. Неудачные попытки входа в таблицу бизнес-аудита
не пишутся: у них нет подтверждённого сотрудника и агента.

Все отказы доступа дают одинаковый `404` с `{"detail":"memory version not available"}`.
Почему не `403`? Ответ `403` сообщил бы, что документ существует, но закрыт.
Тогда перебором идентификаторов можно было бы узнать, какие документы есть
у другой компании. При одинаковом `404` настоящий документ Beta и
несуществующий идентификатор выглядят для агента Alpha одинаково.
Причина отказа сохраняется только в аудите.

Ошибка `503` возвращает `{"detail":"memory storage unavailable"}`. Сообщение БД,
SQL-параметры и текст документа в ответ не попадают. В журнал сервера пишется
только класс исключения.

## 8. Добавить версию через HTTP

```bash
curl -i -X POST \
  -H "Authorization: Bearer $FIN_TOKEN" \
  -H "Idempotency-Key: http-write-1" \
  -H "Content-Type: application/json" \
  -d '{"base_version_id":"policy-v1","expected_number":1,"content":"Fictional HTTP revision two."}' \
  http://127.0.0.1:8005/memory/projects/finance/documents/policy/versions
```

Тело содержит только три поля: базовую версию, ожидаемый текущий номер
и новый текст длиной от 1 до 20 000 символов. Любое лишнее поле, например
`employee_id` или `source`, даёт `422`. Число должно быть числом JSON, а не строкой.

Идентификатор и источник новой версии выбирает сервер:

- `version_id` — UUID 5 от компании, документа и номера. Одинаковый повтор
  получает тот же идентификатор, поэтому совпадает отпечаток запроса этапа 03.
- `source` — `agent:<agent_id>`. Клиент не может записать вымышленный
  «доверенный» источник.

`Idempotency-Key` становится `request_id` из этапа 03. Ключ уникален в рамках
компании, сотрудника и агента: агент другой компании с тем же ключом
не получит чужой результат.

| Попытка | Ответ |
| --- | --- |
| Первая запись | `201`, `replayed: false`, номер 2 |
| Тот же ключ и то же тело | `200`, тот же `version_id`, `replayed: true` |
| Тот же ключ, другой текст | `409`, `idempotency_conflict` |
| Новый ключ, но `expected_number` устарел | `409`, `version_conflict` |
| Нет права записи у сотрудника или действия у агента | `404` |
| Нет или неверный `Idempotency-Key` | `422` |

Ответ на запись содержит метаданные, а не текст: право записи не даёт права
чтения. Новую версию можно прочитать отдельным `GET` с её `version_id`.
У неё будет `source: "agent:fin-agent"`; версия 1 сохраняется без изменений.

## 9. Повторная проверка под блокировкой

Проверка токена и сама операция — разные шаги. Между ними администратор
может отозвать токен. Если бы хранилище доверяло результату первого шага,
отозванный токен успел бы прочитать документ.

Поэтому маршрут передаёт `credential_id` в `MemoryStore`. После блокировки
строки компании хранилище снова читает запись учётных данных. Она должна
быть активной, не истёкшей на момент операции и относиться к тому же агенту
и сотруднику. Иначе операция отклоняется с причиной `credential_unavailable`
и записывается в аудит. Изменения прав и токенов, выполненные под той же
блокировкой компании, упорядочены с операциями памяти.

Тот же порядок защищает повтор записи: если токен отозван, сохранённый
успешный результат идемпотентности не возвращается.

## 10. Что записывается в аудит

Каждая операция, дошедшая до проверки прав, получает строку `audit_events`
с компанией, проектом, сотрудником, агентом, `credential_id`, ключом запроса,
действием, целью, решением, причиной, результатом и временем сервера.
Токен, его хеш и текст документа в аудит не копируются.

```bash
"$AGENTIC_PG_BIN/psql" -h 127.0.0.1 -p 55435 -U agentic -d agentic_stage04_lab -c "SELECT agent_id, action, result, reason, replayed FROM audit_events ORDER BY occurred_at;"
```

Запрос `422` не доходит до операции памяти и в аудит не попадает: тело
отклонено до транзакции. Ответ `401` тоже не записывается.

## Типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| `401` с правильным на вид токеном | Срок, `active`, та ли БД в `APP_DATABASE_URL` |
| `503 memory storage is not configured` | Задан ли `APP_DATABASE_URL` для процесса Uvicorn |
| `503 memory storage unavailable` | Запущена ли PostgreSQL, применена ли миграция `0002` |
| `404` на свой документ | Проект в пути, делегирование агента и право сотрудника |
| `422` при записи | Лишние поля, строка вместо числа, нет `Idempotency-Key` |
| `409 version_conflict` | `expected_number` не равен текущему номеру версии |
| `credential_lab` отвергает URL | Локальный адрес и имя базы на `_lab` |
| `agent registration not found` | ID агента и `--company` |

## Ограничения

- Токен предъявителя: украденный токен работает до истечения или отзыва.
- Нет TLS, ограничения частоты, блокировки после ошибок и журнала неудачных входов.
- Нет HTTP-команд выпуска и отзыва токенов: это привилегированная настройка.
- Нет списка документов и чтения «последней версии»: идентификатор версии
  нужно знать заранее.
- Владелец PostgreSQL по-прежнему может изменить данные и аудит напрямую.
