# ADR 0004: Agent bearer credentials and the authenticated memory API

- Status: accepted
- Date: 2026-10-24

## Context

Stage 03 reads and appends stored document versions for trusted Python callers.
Those callers supply company, employee and agent IDs, which is acceptable only
inside the process. Exposing memory over HTTP requires the server to establish
the acting agent and the employee it represents. A request field, query
parameter or custom header naming an employee cannot provide that proof.

The learning build has no corporate identity provider. It still needs a
mechanism that the server can verify, revoke and test with fictional data.
The selected mechanism must not be described as corporate single sign-on.

## Decision

Authenticate agents with opaque bearer credentials. A credential has the form
`aik1_` followed by 43 URL-safe characters generated by `secrets.token_urlsafe(32)`,
about 256 bits of randomness. The plain token is returned once, at issuance.
PostgreSQL stores only its SHA-256 digest. A fast digest is sufficient because
the token is random rather than a human password.

Each `agent_credentials` row belongs to one company and references the agent
registration `(company_id, agent_id, employee_id)`. Expiry is mandatory, and the
`active` flag revokes a credential. Issuance is privileged laboratory setup,
not an agent operation or employee self-service.

The HTTP layer accepts only `Authorization: Bearer <token>`. A missing,
malformed, unknown, revoked or expired credential receives the same `401`
response with `WWW-Authenticate: Bearer`. Such requests have no trusted actor
and are not stored as business audit rows. Authentication yields a principal
containing company, employee, agent and credential IDs. The employee comes from
the server-side agent registration bound to the credential, never from the request.

Memory routes build an `AccessRequest` from that principal and the path. They
pass the credential ID to `MemoryStore`. After locking the company row, the store
checks the credential again: it must exist, be active, be unexpired at the
operation time and match the request's agent and employee. Otherwise the
operation is denied with `credential_unavailable` and audited. This prevents a
revocation committed between authentication and the locked operation from being
ignored. The existing policy then checks company, project, employee, agent,
delegation, document, version and grant. Audit rows record the credential ID.

Expose two operations:

- `GET /memory/projects/{project_id}/documents/{document_id}/versions/{version_id}`
  returns one authorized version with `Cache-Control: no-store`.
- `POST /memory/projects/{project_id}/documents/{document_id}/versions` appends
  the next version. It requires `Idempotency-Key`, the base version ID, the
  expected current number and new content.

The server derives the new version ID as a UUID 5 of company, document and
number. Provenance is `agent:<agent_id>`. Clients cannot choose either value.
New writes return `201`, identical retries `200` with `replayed: true`. Version
and idempotency conflicts return `409`. Every authorization denial returns the
same `404` body, so a document of another company, another project or with no
grant cannot be distinguished from a missing one. Database or mandatory audit
failure returns `503` without document content.

The web application connects to PostgreSQL only when `APP_DATABASE_URL` is
configured. Otherwise memory routes return `503`. `GET /health` remains liveness
only and does not probe the database.

## Alternatives

- Signed JWTs would avoid a database lookup, but require key management, a
  revocation strategy and claim validation. The current design must recheck
  stored rights anyway.
- An external OpenID Connect provider or corporate SSO is the expected
  production direction, but cannot be verified in this fictional local lab.
- Mutual TLS requires certificate issuance and proxy configuration beyond the
  current stage.
- Trusting `employee_id` in headers or bodies was rejected because any caller
  could choose another employee.

## Consequences

The service establishes agent identity server-side, and agents cannot exceed
the employee rights intersected with their delegation. A stolen bearer token
still impersonates its agent until it expires or is revoked. Outside loopback
it must travel only over TLS. No rate limiting, lockout or persisted record of
failed authentication exists yet.

The employee is not authenticated interactively. Their authority comes from
trusted registration, delegation and grant records created by laboratory setup.
A production deployment would need corporate identity integration for issuing
credentials, rotation, secret storage, transport security and monitoring.
These require separate decisions and evidence.
