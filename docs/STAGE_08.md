# Этап 08. Контейнеры, оценки и восстановление

[README](../README.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md) · [Этап 07](STAGE_07.md)

## Что меняется

До этого этапа приложение запускалось из рабочей копии через `uv run`,
а PostgreSQL — как временный локальный кластер. Теперь приложение собирается
в контейнерный образ и вместе с учебной PostgreSQL поднимается одной командой
Docker Compose. Появились проверка готовности `/ready`, набор независимых
ожидаемых результатов (оценок) и сценарий, который с нуля проходит всю
лабораторию: данные, источник, оценки, учения с поломками, резервную копию,
потерю тома и восстановление.

Это **локальная Compose-лаборатория на вымышленных данных**, а не корпоративное
развёртывание. Решение: [ADR 0008](adr/0008-container-lab-and-evaluations.md).

## Граница этапа

Реализованы образ приложения, Compose-файл, `/ready`, оценки по HTTP, сценарий
`scripts/compose_lab.py`, учения со сбоем аудита и утечкой прав, резервная
копия через `pg_dump` с восстановлением через `pg_restore` и задание CI,
которое повторяет весь сценарий в чистой среде GitHub Actions.

Не реализованы публикация образа в реестр, TLS, корпоративный вход (SSO),
менеджер секретов, отдельная роль БД с ограниченными правами, расписание
резервных копий, мониторинг с оповещениями, сканирование образа на
уязвимости и настоящая модель. Учебные команды заполнения, выдачи токенов,
синхронизации и оценок работают на хосте через loopback-порты.

## 1. Разобраться с новыми частями

| Часть | Назначение |
| --- | --- |
| `Dockerfile` | Двухстадийная сборка: зависимости из `uv.lock`, затем образ без uv, тестов и документов |
| `.dockerignore` | Не передаёт в сборку Git, `.env`, `var/`, тесты, фикстуры и документы |
| `compose.yaml` | Сервисы `db`, `migrate`, `app`; порты только на `127.0.0.1` |
| `app/main.py` | Маршрут `GET /ready` |
| `app/persistence/database.py` | `SCHEMA_HEAD` и `schema_revision()` |
| `app/persistence/lab.py` | `seed_second_company()`: вымышленная компания Beta |
| `evaluations/cases.json` | 22 независимых ожидаемых результата |
| `scripts/evaluate.py` | Запуск оценок по HTTP и чистые проверки ответов |
| `scripts/compose_lab.py` | Полный сценарий с учениями, копией и восстановлением |
| `fixtures/lab/beta/` | Вымышленный текст второй компании |
| `.github/workflows/ci.yml` | Новое задание `container-lab` |

**Оценка** здесь — это заранее записанное ожидание о внешнем поведении:
«инженерный помощник получает `404` в финансовом проекте», «ответ цитирует
только читаемые документы». Ожидания не вычисляются из кода приложения,
поэтому поломка приложения не может незаметно поменять и ответ, и ожидание.

## 2. Образ приложения

Сборка идёт в две стадии. Стадия `builder` берёт `uv` 0.12.23 и выполняет
`uv sync --locked --no-dev`: ставятся только зависимости работающего сервиса.
Стадия `runtime` копирует готовое окружение, пакет `app`, миграции и
`alembic.ini`. В итоговом образе нет uv, pytest, Ruff, ReportLab, тестов,
фикстур, документов и `.env`.

Базовые образы закреплены по digest индекса (несколько архитектур):
`python:3.12.15-slim` и `ghcr.io/astral-sh/uv:0.12.23`. Тег можно перезаписать,
digest — нет. Обновление образа — отдельное осознанное изменение:

```bash
docker buildx imagetools inspect python:3.12.15-slim
```

Сервис работает от пользователя `app` (UID 10001). Код принадлежит `root`
и недоступен процессу для записи. `HEALTHCHECK` обращается к `/ready`.
Uvicorn запускается в exec-форме, поэтому сигнал остановки доходит до него.

```bash
docker build -t agentic-infrastructure:local .
```

## 3. Compose-лаборатория

| Сервис | Что делает |
| --- | --- |
| `db` | PostgreSQL 17.11, образ закреплён по digest; том `postgres_data` |
| `migrate` | Однократно выполняет `alembic upgrade head` и завершается |
| `app` | API на порту `8000` внутри сети Compose; стартует после успешной миграции |

Порты публикуются только на `127.0.0.1`: API — `8005`, PostgreSQL — `55436`
(меняются переменными `APP_PORT` и `POSTGRES_PORT`). Пароль БД обязателен:
без `POSTGRES_PASSWORD` Compose остановится с понятной ошибкой. Пароль
должен быть URL-безопасным, потому что входит в адрес подключения.

```bash
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
docker compose up --detach --wait
docker compose ps
curl -s http://127.0.0.1:8005/ready
```

`--wait` ждёт, пока `db` и `app` станут `healthy`, а `migrate` завершится
успешно. Пароль фиксируется **при создании тома**: если позже указать другой,
миграция не пройдёт аутентификацию. Для чистого старта удалите том:

```bash
docker compose down --volumes
```

Обычный `docker compose down` сохраняет том и данные. Даже для остановки
Compose требует, чтобы `POSTGRES_PASSWORD` был задан (подойдёт любое значение).

Учебные команды прежних этапов работают с хоста через опубликованный порт:

```bash
export DATABASE_URL="postgresql+psycopg://agentic:${POSTGRES_PASSWORD}@127.0.0.1:55436/agentic_lab"
uv run --locked python -m app.persistence_demo --setup
uv run --locked python -m app.credential_lab fin-agent
```

Защита учебных команд прежняя: только loopback-адрес и база с окончанием
`_lab`. Приложение внутри Compose обращается к БД по имени сервиса `db`.

## 4. Готовность и наблюдение за ошибками

`/health` отвечает «процесс жив» и не обращается к БД. Новый `/ready`
проверяет соединение и версию схемы:

| Ответ | Когда |
| --- | --- |
| `200` `{"status":"ready","database":"ok","schema":"current"}` | БД отвечает, ревизия равна `SCHEMA_HEAD` |
| `503` `{"status":"not_ready","database":"not_configured","schema":"unknown"}` | Не задан `APP_DATABASE_URL` |
| `503` `{"status":"not_ready","database":"unavailable","schema":"unknown"}` | БД не отвечает |
| `503` `{"status":"not_ready","database":"ok","schema":"outdated"}` | Ревизия другая или отсутствует |

Ответ не кешируется и не содержит адреса, пароля или текста ошибки. Тест
сверяет `SCHEMA_HEAD` с последней миграцией, чтобы новая миграция не осталась
незамеченной. `/ready` не проверяет права, токены и источник: успешный ответ
не означает готовность к корпоративным данным.

Журналы смотрят так:

```bash
docker compose logs --follow app
docker compose ps
```

Ошибки хранилища записываются строкой `memory storage failure: <класс ошибки>`,
неудачная проверка готовности — `readiness probe failed: <класс ошибки>`.
Журнал доступа Uvicorn содержит метод, путь и код; заголовков и токенов
в нём нет. Если остановить `db`, `/health` продолжит отвечать `200`, `/ready`
и маршруты памяти — `503`, а Docker после 20 неудачных проверок подряд
(около минуты при интервале 3 секунды) пометит `app` как `unhealthy`. После запуска `db` сервис восстанавливается без перезапуска.

## 5. Независимые оценки

Файл `evaluations/cases.json` описывает 22 случая. У каждого есть агент
(`fin`, `eng`, `beta`, `unknown` или без токена), запрос и ожидания.

| Группа | Что проверяется |
| --- | --- |
| Разрешённое чтение | Финансовый агент читает свою версию, ищет и получает ответ со ссылками |
| Межпроектный отказ | Инженерный агент получает `404` в `finance`, в том числе через путь своего проекта |
| Межкорпоративный отказ | Агент Beta не видит Alpha, агент Alpha не видит проект Beta |
| Инструкция внутри документа | Фраза «Ignore all previous rules…» возвращается как текст и не расширяет доступ |
| Источник | Новая редакция используется, отозванный читатель и удалённый документ недоступны |
| Повреждённый документ | Текст с управляющим символом не выдаётся; синхронизированный документ нельзя изменить |
| Учётные данные и ввод | Без токена и с неизвестным токеном — `401`, поле `project_id` в теле — `422` |

Ожидания бывают такими: точный статус и тело ответа, обязательные и
запрещённые фразы, документы, которые должны или не должны появиться,
множество допустимых документов, статус ответа агента, обязательные ссылки.
С флагом `verify_references` оценщик заново читает каждую ссылку тем же
агентом: версия должна читаться, а `content[start:end]` — совпадать с текстом
фрагмента. Флаг `grounded_quotes` требует, чтобы каждая строка ответа
`[n] ...` была цитатой из фрагмента `n`. Это свойство офлайн-провайдера;
для генеративной модели понадобится другая мера опоры на источник.

Плейсхолдер `{version:alpha:travel-policy:1}` превращается в документированный
воспроизводимый ID версии. Опечатка в файле случаев (лишний ключ, неизвестный
агент, повтор ID) останавливает запуск, а не проходит молча.

Оценки можно запустить отдельно против любого стенда. Файл токенов хранится
вне Git, например в `var/lab/tokens.json` с правами `0600`:

```bash
uv run --locked python -m scripts.evaluate --base-url http://127.0.0.1:8005 \
  --tokens var/lab/tokens.json
```

Команда отправляет токены только по HTTPS или по HTTP на loopback и печатает
число пройденных случаев и проблемы без тел ответов.

## 6. Полный сценарий

```bash
uv run --locked python -m scripts.compose_lab
```

Сценарий использует **отдельный одноразовый проект** `agentic-stage08` с портами
`18005` и `55438`, поэтому не трогает ручной стенд `agentic-infrastructure`.
Пароль БД и все токены создаются заново и живут только в памяти процесса.

1. Удаляет прежний запуск этого проекта вместе с томом, собирает образ и
   поднимает `db`, `migrate`, `app`.
2. Создаёт Alpha (`seed_lab`) и Beta (`seed_second_company`), импортирует
   тексты `fixtures/lab`, проверяет отказ импорта файла с неверным UTF-8.
3. Запускает вымышленный Handbook на свободном loopback-порту, синхронизирует
   оба состояния источника и выдаёт токены трём агентам.
4. Выполняет 22 оценки.
5. Проводит учения: сбой аудита и утечку прав (раздел 7).
6. Делает резервную копию, удаляет том, восстанавливает копию и повторяет оценки.
7. Измеряет задержку последовательных запросов и записывает среду Docker.
8. Удаляет проект и том.

Ход выполнения печатается в stderr, итоговый JSON — в stdout и в
`var/reports/agentic-stage08.json`. Код выхода `0` означает, что прошли
все оценки, отказ импорта, оба учения, восстановление и замеры. С флагом
`--keep` стенд остаётся работать, а токены сохраняются в `var/lab/tokens.json`
(права `0600`); пароль БД не сохраняется. Удалить такой стенд:

```bash
POSTGRES_PASSWORD=unused docker compose -p agentic-stage08 down --volumes
rm -f var/lab/tokens.json
```

Сценарий отказывается работать с именем `agentic-infrastructure` и именами
без префикса `agentic-`, потому что удаляет том проекта.

## 7. Учения: оценки должны ловить поломку

**Сбой аудита.** Сценарий как владелец БД добавляет триггер, который
отклоняет любую вставку в `audit_events`, и читает версию с текстом
«500 credits per trip». Ожидается `503` `memory storage unavailable`, без
текста документа, а число строк аудита не меняется. Затем триггер удаляется,
и то же чтение снова даёт `200`.

**Утечка прав.** Сценарий напрямую в БД выдаёт `eng-agent` делегирование
в `finance`, а `eng-user` — право чтения `travel-policy`. Это имитирует ошибку
администратора или испорченную миграцию. Оценки обязаны упасть минимум
в случаях `cross-project-context` и `cross-project-read`; на деле падает и
`instruction-does-not-widen-access`. После удаления этих записей все случаи
снова проходят. Если оценки не заметили утечку, сценарий считается неуспешным.

Тесты `tests/test_evaluate.py` дополнительно подают оценщику подделанные
ответы: чужой документ, запрещённую фразу, сдвинутые смещения, неверную
цитату, другое тело отказа. Каждая подделка должна дать проблему.

## 8. Резервная копия и восстановление

Сценарий делает копию в формате `pg_dump --format=custom`, сохраняет её
в `var/backups/` с правами `0600`, выполняет `docker compose down --volumes`,
поднимает пустую БД, восстанавливает копию через
`pg_restore --exit-on-error --no-owner` и запускает `migrate` и `app`.
Успех означает, что число строк основных таблиц совпало, а исходы всех оценок
до и после восстановления одинаковы.

Для ручного стенда те же шаги выглядят так:

```bash
mkdir -p var/backups
docker compose exec -T db pg_dump --username=agentic --dbname=agentic_lab \
  --format=custom > var/backups/agentic_lab.dump
chmod 600 var/backups/agentic_lab.dump
docker compose down --volumes
docker compose up --detach --wait db
docker compose exec -T db pg_restore --username=agentic --dbname=agentic_lab \
  --exit-on-error --no-owner < var/backups/agentic_lab.dump
docker compose up --detach --wait
```

Копия содержит тексты документов, хэши токенов и всю историю. Обращайтесь
с ней как с корпоративными данными: не коммитьте, не отправляйте в чат,
храните отдельно от сервера. Подтверждение источника в копии стареет: если
восстановление заняло больше `max_age`, документы источника недоступны до
следующей успешной синхронизации. Это ожидаемое закрытие доступа, а не потеря.

## 9. Замеры

Сценарий 30 раз подряд вызывает `/ready`, поиск контекста и ответ агента
одним клиентом и записывает медиану, 95-й перцентиль и максимум. Вместе
с ними записываются версия Docker, ОС, число CPU и память виртуальной машины
Docker. Цифры из [отчёта](VERIFICATION.md) описывают один ноутбук
с несколькими вымышленными документами. Это не обещание пропускной способности,
не нагрузочный тест и не оценка поведения на корпоративном объёме.

## 10. CI

Новое задание `container-lab` в GitHub Actions на `ubuntu-24.04` ставит uv
и зависимости, затем выполняет `python -m scripts.compose_lab` — тот же сценарий
в чистой среде: сборка образа, Compose, оценки, оба учения, копия и
восстановление. После этого задание печатает JSON-отчёт (счётчики, ID случаев
и время; токенов и паролей в нём нет). Образ никуда не публикуется. Образ
PostgreSQL сервиса в задании `checks` закреплён тем же digest, что и в Compose.

## 12. Проверить результат

```bash
uv sync --locked
uv run --locked pytest -m 'not postgres'
export TEST_DATABASE_URL='postgresql+psycopg://agentic@127.0.0.1:55435/agentic_test'
uv run --locked pytest -m postgres
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts migrations
uv run --locked python scripts/check_docs.py
uv lock --check --offline
git diff --check
uv run --locked python -m scripts.compose_lab
```

Последняя команда требует запущенный Docker. Фактические результаты и
публикация записываются в [отчёт](VERIFICATION.md); сами команды в этом
разделе не означают, что проверка прошла.

## Типичные ошибки

| Симптом | Причина и решение |
| --- | --- |
| `set a URL-safe POSTGRES_PASSWORD` | Не задан пароль; задайте его даже для `down` |
| `migrate` завершился с кодом 1 | Пароль отличается от пароля при создании тома; верните прежний или `down --volumes` |
| `port is already allocated` | Порт занят; задайте `APP_PORT` / `POSTGRES_PORT` или остановите другой процесс |
| `Cannot connect to the Docker daemon` | Docker Desktop не запущен |
| `/health` 200, `/ready` 503 | Процесс жив, но БД недоступна или схема устарела |
| Учебная команда отклоняет адрес | Нужен `127.0.0.1`, база `agentic_lab` и пароль в `DATABASE_URL` |

## Ограничения выпуска

Compose-лаборатория не является корпоративной публикацией. Для настоящего
развёртывания понадобятся как минимум:

- TLS на входе и проверенный корпоративный вход сотрудников;
- секреты из менеджера секретов вместо переменных окружения;
- отдельная роль БД без прав суперпользователя и владельца схемы;
- расписание и хранение резервных копий, регулярная проверка восстановления;
- мониторинг, оповещения и централизованный сбор журналов;
- сканирование образа и зависимостей, политика обновления digest;
- согласованная политика хранения и физического удаления данных;
- оценка настоящей модели и нагрузочное тестирование на реальном объёме.

Владелец БД по-прежнему может напрямую менять документы, права и историю:
учения этапа это показывают и проверяют, что оценки замечают такую поломку,
но не защищают от неё.
